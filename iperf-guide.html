iperf / iperf3 완전 정리

네트워크 성능 측정 도구 사용법 및 실전 예제. iperf2 · iperf3 차이부터 BDP 계산, UDP 튜닝, 결과 진단 패턴, 대표 오류 해결까지 실무 기준으로 정리합니다.

TCP / UDP 처리량 측정 iperf3 3.16+ 멀티스레드 JSON 자동화 연동 DSCP / Congestion Control

01 iperf2 vs iperf3

iperf 계열은 iperf2(iperf 바이너리)와 iperf3(iperf3 바이너리) 두 갈래로 완전히 분리되어 있습니다. 이름만 비슷할 뿐 프로토콜 호환성은 없습니다. 먼저 두 계열의 차이를 명확히 구분합니다.

iperf2

// iperf 바이너리
  • NLANR/UIUC 계열에서 출발한 오래된 코드베이스
  • 기본 포트 5001
  • 멀티스레드를 오래전부터 지원
  • JSON 출력 없음
  • 역방향/양방향 지원이 버전별로 상이
  • 인증 기능 제한적

iperf3

// iperf3 바이너리
  • ESnet이 전면 재작성한 신규 구현
  • 기본 포트 5201
  • 3.15 이하는 사실상 단일 스레드 / 3.16+부터 -P 스트림별 스레드
  • JSON 출력 -J 공식 지원
  • 역방향 -R(3.1+), 양방향 --bidir(3.7+)
  • RSA 키 + 사용자 인증 지원
항목iperf2 (iperf)iperf3 (iperf3)
개발NLANR/UIUC 계열ESnet 전면 재작성
기본 포트50015201
상호 호환불가불가
멀티스레드오래전부터 지원3.15 이하 사실상 단일 스레드 / 3.16+ -P 스트림별 스레드
JSON 출력없음-J 공식 지원
역방향/양방향버전별 상이-R(3.1+), --bidir(3.7+)
인증제한적RSA 키 + 사용자 인증
✗
가장 흔한 실수

iperf2 서버에 iperf3 클라이언트로 붙는 것. 프로토콜이 완전히 달라 절대 연결되지 않습니다. 양쪽 모두 같은 계열이어야 합니다.

3.16 멀티스레드 변경이 중요한 이유: 이전에는 25/40/100G 환경에서 -P 16을 줘도 CPU 코어 하나가 병목이었습니다. 3.16부터 각 스트림이 별도 스레드로 처리되어 멀티코어를 실제로 활용합니다.

03 동작 원리

iperf3 세션은 하나의 TCP 제어 연결과, 실제 측정용 데이터 연결(TCP 또는 UDP)로 구성됩니다. 클라이언트가 먼저 서버의 TCP 5201 제어 포트로 접속해 테스트 파라미터를 협상하고, 이어서 데이터 스트림을 주고받은 뒤, 마지막으로 결과 통계를 교환합니다.

i
핵심

UDP 테스트에도 제어용 TCP 5201 연결이 필요합니다. 방화벽에 TCP와 UDP를 모두 열어야 합니다.

07 UDP 옵션

옵션설명
-uUDP 모드
-b rate목표 비트레이트 (UDP 기본값 1Mbps — 반드시 지정할 것)
--fq-rate rateLinux FQ 기반 pacing
--pacing-timer us애플리케이션 pacing 주기
--udp-counters-64bit64비트 카운터
⚠
주의 1

-b는 "최대 속도 자동 탐색"이 아닙니다. 지정한 속도로 밀어넣을 뿐입니다. 링크 용량보다 높게 주면 손실이 나는 게 정상입니다.

⚠
주의 2

-P n과 -b를 함께 쓰면 비트레이트가 스트림당 적용됩니다. -P 4 -b 100M = 총 400Mbps.

08 실전 예제

서버는 먼저 iperf3 -s 실행. 아래는 클라이언트 명령입니다.

8.1 기본 TCP

BASH
iperf3 -c 192.0.2.10                    # 기본 10초 측정
iperf3 -c 192.0.2.10 -t 30 -i 1         # 30초, 1초 간격 출력
iperf3 -c 192.0.2.10 -f m               # Mbit/s 단위 고정
iperf3 -c 192.0.2.10 -V                 # 소켓/주소 상세 정보
iperf3 -c 192.0.2.10 -n 1G              # 1GiB 전송 후 종료
iperf3 -c 192.0.2.10 -F ./testfile      # 특정 파일로 전송

8.2 병렬 / 방향

BASH
iperf3 -c 192.0.2.10 -P 4 -t 30          # 4개 병렬 스트림
iperf3 -c 192.0.2.10 -P 16 -t 30         # 고속망 스케일 테스트
iperf3 -c 192.0.2.10 -R                  # 역방향 (다운로드 측정)
iperf3 -c 192.0.2.10 --bidir -t 30       # 양방향 동시
iperf3 -c 192.0.2.10 --get-server-output # 서버 측 통계까지 확인

8.3 UDP

BASH
iperf3 -c 192.0.2.10 -u -b 100M -t 30       # 100Mbps UDP
iperf3 -c 192.0.2.10 -u -b 1G -t 30 -i 1    # 1Gbps, 초당 지터/손실 추적
iperf3 -c 192.0.2.10 -u -b 500M -l 1200     # 데이터그램 1200B (MTU 여유)
iperf3 -c 192.0.2.10 -u -b 1G --fq-rate 1G  # FQ pacing으로 버스트 완화

손실이 시작되는 지점 탐색:

BASH
for r in 100M 300M 500M 800M 1G; do
  echo "=== $r ==="
  iperf3 -c 192.0.2.10 -u -b $r -t 10 | tail -4
done

8.4 MTU / MSS / 윈도우

BASH
iperf3 -c 192.0.2.10 -M 1460            # 표준 Ethernet MSS
iperf3 -c 192.0.2.10 -M 1200            # VPN/터널 환경 가정
iperf3 -c 192.0.2.10 -N                 # Nagle 비활성화
iperf3 -c 192.0.2.10 -w 4M              # 윈도우 4MiB
iperf3 -c 192.0.2.10 -w 32M -t 30       # 장거리 고대역 경로
BDP 계산 윈도우 크기 결정 기준
Bandwidth-Delay Product. 이 값보다 TCP 윈도우가 작으면 회선 대역폭을 다 채울 수 없습니다.
BDP(bytes) = 대역폭(bps) × RTT(sec) / 8
예) 10Gbps, RTT 20ms
10,000,000,000 × 0.020 / 8 = 25,000,000 B ≈ 24 MiB

윈도우가 BDP보다 작으면 단일 TCP 흐름은 절대 링크를 채울 수 없습니다. -w를 늘리거나 -P로 스트림을 늘려야 합니다.

8.5 JSON / 자동화

BASH
iperf3 -c 192.0.2.10 -J > result.json

# 평균 수신 bitrate
iperf3 -c 192.0.2.10 -J | jq '.end.sum_received.bits_per_second'

# 구간별 bitrate
iperf3 -c 192.0.2.10 -J | jq '.intervals[].sum.bits_per_second'

# TCP 재전송 수
iperf3 -c 192.0.2.10 -J | jq '.end.sum_sent.retransmits'

# UDP 손실률
iperf3 -c 192.0.2.10 -u -b 500M -J | jq '.end.sum.lost_percent'

# Mbps로 보기 좋게
iperf3 -c 192.0.2.10 -J | jq '.end.sum_received.bits_per_second/1e6 | round'

8.6 서버 운용

BASH
iperf3 -s -D                            # 데몬 모드
iperf3 -s -D -I /run/iperf3.pid         # PID 파일
iperf3 -s -p 5202                       # 다른 포트
iperf3 -s -1                            # 1회만 처리 후 종료
iperf3 -s -B 10.0.0.5                   # 특정 인터페이스만 수신

# 동시 다중 측정 → 포트별 인스턴스
for p in 5201 5202 5203; do iperf3 -s -p $p -D; done

8.7 IPv6

BASH
iperf3 -s -6
iperf3 -6 -c 2001:db8::10
iperf3 -4 -c 192.0.2.10                 # IPv4 강제

8.8 DSCP / QoS

⚠
주의

-S는 DSCP 값이 아니라 ToS 바이트 전체 값입니다. DSCP는 상위 6비트이므로 DSCP × 4를 넣어야 합니다.

DSCP이름-S 값 (10진)16진
46EF1840xB8
34AF411360x88
26AF311040x68
0BE00x00
BASH
iperf3 -c 192.0.2.10 -S 184             # DSCP EF (46)
iperf3 -c 192.0.2.10 -S 0xB8            # 동일 (16진 표기)

# 최신 버전은 --dscp 지원 여부 확인
iperf3 --help | grep -i dscp
iperf3 -c 192.0.2.10 --dscp 46          # 지원 시 이게 직관적

수신 측에서 실제 마킹 보존 여부를 함께 캡처해야 합니다:

BASH
sudo tcpdump -i eth0 -v 'tcp port 5201' | grep -i tos

8.9 Congestion Control 비교

BASH
sysctl net.ipv4.tcp_available_congestion_control   # 사용 가능 목록 확인

iperf3 -c 192.0.2.10 -C cubic -t 30
iperf3 -c 192.0.2.10 -C bbr   -t 30

# BBR 모듈이 없으면 로드
sudo modprobe tcp_bbr

고지연·저손실 경로에서는 BBR이, 저지연 데이터센터에서는 CUBIC이 유리한 경향이 있습니다.

8.10 방화벽

BASH
# firewalld
sudo firewall-cmd --permanent --add-port=5201/tcp
sudo firewall-cmd --permanent --add-port=5201/udp
sudo firewall-cmd --reload

# ufw
sudo ufw allow 5201/tcp && sudo ufw allow 5201/udp

# 도달성 확인
nc -vz 192.0.2.10 5201

09 결과 해석

9.1 TCP

[ ID] Interval           Transfer     Bitrate         Retr  Cwnd
[  5]  0.00-1.00  sec   118 MBytes   986 Mbits/sec    0    412 KBytes
[  5]  0.00-10.00 sec  1.10 GBytes   945 Mbits/sec   12
필드의미판단 기준
Transfer구간 전송량—
BitrateTransfer × 8 / 시간. 애플리케이션 계층 속도1G 링크에서 940~950Mbps면 정상 (헤더 오버헤드)
RetrTCP 재전송 세그먼트 수0에 가까워야 정상. 많으면 손실/혼잡/NIC 문제
Cwndcongestion window작은데 늘지 않으면 손실 또는 윈도우 제한

진단 패턴

Cwnd 작음 + Retr 많음
추정 원인: 경로 패킷 손실 / 혼잡
↓
Cwnd 큼 + Bitrate 낮음
추정 원인: 수신 측 CPU, 버퍼, 애플리케이션 병목
↓
Retr 0 + Bitrate 낮음 + RTT 높음
추정 원인: 윈도우 부족 (BDP 대비 -w 상향 필요)

9.2 UDP

[  5]  0.00-10.00 sec  119 MBytes  100 Mbits/sec  0.123 ms  12/85000 (0.014%)
                                                   ^Jitter   ^Lost/Total (손실률)
필드의미기준
Jitter도착 간격 변동VoIP 기준 30ms 이하 권장
Lost/Total유실/전체 데이터그램VoIP·영상 1% 이하

UDP는 재전송이 없으므로 손실 = 실제 데이터 유실입니다. 단, 손실률만 보지 말고 지터를 반드시 함께 확인하세요. 손실 0%여도 지터가 크면 실시간 트래픽은 품질이 나쁩니다.

10 함정과 베스트 프랙티스

1 CPU가 병목인지 먼저 의심

10G 이상, 작은 패킷, 고속 UDP, VM/컨테이너 환경에서는 iperf3 자체가 병목입니다.

BASH
mpstat -P ALL 1        # 한 코어가 100%면 네트워크가 아니라 iperf3 문제
iperf3 -c SERVER -Z    # zero-copy로 CPU 절감
iperf3 -c SERVER -A 2  # 특정 코어 고정 (인터럽트 코어와 분리)

2 단일 스트림의 한계

높은 RTT, 작은 윈도우, congestion control, ECMP 해시 때문에 단일 TCP는 링크를 못 채웁니다. 반드시 비교 측정하세요.

BASH
iperf3 -c SERVER -t 30
iperf3 -c SERVER -P 4 -t 30
iperf3 -c SERVER -P 8 -t 30

-P는 무작정 늘리면 컨텍스트 스위칭 오버헤드로 오히려 나빠집니다. 보통 4~8에서 포화됩니다.

3 측정 시간

최소 10초, 운영 검증은 30초 이상. TCP slow start를 빼려면 -O 5. 단, 초기 응답 성능을 보려는 목적이면 -O를 쓰면 안 됩니다.

4 무선 환경

RSSI, 채널 폭, MCS, 간섭, 절전 모드에 크게 좌우됩니다. TCP bitrate 하나로 유선과 비교하지 말고 UDP 지터·손실을 함께 측정하세요.

5 클라우드 / 컨테이너

Security Group, NACL, 호스트 방화벽, NetworkPolicy, Docker 포트 매핑, NAT를 모두 확인해야 합니다.

6 공개 서버

iperf.fr 서버 목록이 있지만 혼잡·rate limit·정책 위반 위험이 있습니다. 운영 측정은 직접 관리하는 서버로 하세요. 특히 공개 서버에 고속 UDP를 쏘면 서비스 방해가 됩니다.

11 대표 오류 해결

에러원인해결
unable to connect to server 서버 미실행, 포트/IP 오류, 방화벽, IPv4/6 불일치, iperf2↔iperf3 혼용 nc -vz IP 5201, iperf3 --version 양쪽 확인, -4/-6 명시
control socket has closed unexpectedly 서버 종료, 버전 불일치, 중간 방화벽 세션 끊김, 리소스 부족 옵션 없이 기본 테스트로 축소 후 하나씩 추가하며 원인 격리
the server is busy running a test 서버가 다른 테스트 처리 중 / 이전 세션 미정리 대기 후 재시도, ps aux | grep iperf3, 포트별 인스턴스 분리
unable to set TCP_CONGESTION 해당 알고리즘 모듈 없음 sysctl net.ipv4.tcp_available_congestion_control 확인, modprobe tcp_bbr
unable to set socket buffer size OS 최대 버퍼 제한 sysctl net.core.rmem_max wmem_max 확인 후 상향 또는 -w 축소
UDP 손실률 과다 과부하, 방화벽, MTU 초과, 수신 CPU, 버퍼 부족 -b 낮춰 재측정, -l 1200, net.core.rmem_max 상향
에러 발생
연결 실패 / 소켓 종료 / 손실률 과다 중 하나로 분류

최소 옵션으로 재현 후 원인 확정

소켓 버퍼 상향 (고속 환경 필수 튜닝):

BASH
sudo sysctl -w net.core.rmem_max=268435456
sudo sysctl -w net.core.wmem_max=268435456
sudo sysctl -w net.ipv4.tcp_rmem="4096 87380 268435456"
sudo sysctl -w net.ipv4.tcp_wmem="4096 65536 268435456"

12 권장 측정 절차

TCP 경로 검증

  1. 베이스라인 측정
    옵션 없이 기본 10초 테스트
    BASH
    iperf3 -c SERVER -t 10
  2. 안정성 확인
    30초, 1초 간격 중간 결과로 변동 관찰
    BASH
    iperf3 -c SERVER -t 30 -i 1
  3. 병렬 스케일 테스트
    4개 병렬 스트림으로 단일 흐름 한계 확인
    BASH
    iperf3 -c SERVER -P 4 -t 30
  4. 역방향 측정
    서버 → 클라이언트 방향 (다운로드 경로)
    BASH
    iperf3 -c SERVER -R -t 30
  5. 양방향 동시 측정
    업/다운 동시 부하에서의 실제 처리량 확인
    BASH
    iperf3 -c SERVER --bidir -t 30
  6. 최종 기록
    slow start 제외, JSON으로 결과 보존
    BASH
    iperf3 -c SERVER -P 4 -t 30 -O 5 -J > tcp.json

UDP 검증

BASH
iperf3 -c SERVER -u -b 100M -t 30
iperf3 -c SERVER -u -b 500M -t 30
iperf3 -c SERVER -u -b 1G   -t 30
결과 기록 시 함께 남겨야 할 항목
iperf3 버전, 방향, 병렬 스트림 수, -w/-M 설정, RTT, CPU 사용률, TCP 재전송 수, UDP 손실률·지터, 링크 속도, MTU.

이 맥락 없는 bitrate 숫자 하나는 재현도 비교도 불가능합니다.
