1. 왜 Anycast RP인가 — 문제 정의#

멀티캐스트 Sparse Mode에서 RP는 source와 receiver를 처음 연결해 주는 control-plane 중심점이다. 그래서 RP 하나만 두면 구성은 단순해 보이지만, 실제 운영에서는 장애와 수렴 관점에서 부담이 커진다.

단일 RP의 구조적 한계

  • SPOF: RP node 자체 장애, loopback reachability 상실, 또는 RP 인접 구간 장애가 곧 서비스 영향으로 이어진다.
  • 수렴 지연: RP 장애 후 새 RP로 전환되는 동안 Register/Join 흐름이 재정렬된다.
  • 확장성 제약: 대규모 그룹/소스 환경에서 제어 트래픽과 상태 관리가 한 노드에 집중된다.

Auto-RP/BSR와 Anycast RP의 위치

Auto-RP/BSR은 “어떤 RP를 사용할지”를 알리는 discovery 메커니즘이다. 반면 Anycast RP는 “동일 RP 주소를 여러 장비가 공유해, IGP 최단경로로 가장 가까운 RP에 붙게 만드는” 가용성/수렴 메커니즘이다. 즉, 역할이 다르다.

핵심 아이디어는 간단하다. 여러 RP에 동일한 /32(예: 5.1.1.1/32)를 부여하고 IGP에 광고하면, source DR과 receiver LHR은 유니캐스트 라우팅 기준으로 가까운 RP를 자동 선택한다.

그런데 여기서 바로 질문이 나온다. “각 RP가 source 정보를 서로 어떻게 맞출 것인가?” 이 질문이 곧 PIM Anycast-RP(RFC 4610)와 MSDP Anycast-RP(RFC 3446, RFC 3618) 분기점이다.

한 문장 요약
Anycast RP의 본질은 RP 선택을 IGP로 단순화하는 데 있고, 실무 선택지는 source state 동기화를 PIM Register로 할지, MSDP SA로 할지다.

3. PIM Anycast-RP (RFC 4610) 동작 원리#

PIM Anycast-RP는 “별도 프로토콜 없이 PIM Register 자체를 RP 간 복제”한다. 그래서 intra-domain NX-OS 환경에서 운영 단순성이 높다. 이 메커니즘이 없으면, source가 RP1에 붙었는데 receiver가 RP2를 향할 때 RP2가 source를 모르는 상태가 지속된다.

3-1. Register 복제 절차 (1~7)

  1. Source DR이 첫 멀티캐스트 패킷을 RP Anycast 주소(5.1.1.1)로 Register encapsulation 하여 전송한다.
  2. IGP 최단경로로 가장 가까운 RP(예: N9K-1)가 Register를 수신한다.
  3. RP1은 Register decapsulation 후 shared tree(또는 정책에 따른 트리)로 전달을 시작한다.
  4. RP1은 (S,G) state를 생성한다.
  5. RP1은 Anycast-RP set의 나머지 멤버(예: 1.1.1.2)에게 Register copy를 전송한다. 이때 source IP는 자신의 unique Lo0이다.
  6. RP1은 DR에 Register-Stop을 보낸다(필요 시 Null-Register 갱신 주기 유지).
  7. RP2는 복제 Register를 기반으로 동일한 (S,G) state를 생성하여 receiver 측 요청에 즉시 대응 가능해진다.

3-2. Loop prevention 규칙 (핵심)

  • RFC 4610 핵심 조건: Register의 source address가 Anycast-RP set member로 식별되면, 그 Register는 다시 다른 멤버로 재복제하지 않는다.
  • 목적: RP set 내부에서 Register 복제 루프가 생기는 것을 원천 차단한다.
  • TTL 처리: 복제 Register는 원본 Register의 TTL 정보를 정책/RFC 규칙에 맞게 복사해 사용한다. TTL을 임의 변형하면 기대한 loop 방지 모델과 디버깅 가정이 깨진다.

3-3. Register-Stop 및 유실 복구

PIM Anycast-RP는 “영구 DB 복제”가 아니라, Register 이벤트를 매개로 source state를 동기화/재생성하는 모델이다. 따라서 복제 Register가 순간 유실될 수는 있다.

이때 DR의 register suppression timer가 만료되면, DR은 다시 Register를 전송한다. RP는 이를 통해 state를 재학습한다. 즉, 단기 유실이 즉시 영구 불능을 의미하지 않는다.

운영 해석
PIM Anycast-RP는 event-driven 재학습 구조다. “복제 패킷 1회 유실 = 영구 장애”가 아니라, timer 기반 재전송으로 회복되는 구조인지 이해해야 정확한 장애 판단이 가능하다.

  ip router ospf 10 area 0

4. MSDP Anycast-RP (RFC 3446 + RFC 3618) 동작 원리#

MSDP Anycast-RP는 RP 간 source 존재 사실을 SA(Source-Active)로 교환한다. PIM Anycast-RP와 달리, 별도 TCP 세션과 SA cache가 들어와 control-plane 복잡도가 증가하지만, inter-domain 또는 멀티벤더 연동에 유리하다.

4-1. SA 기반 source discovery 절차

  1. RP1이 local source의 Register를 받아 (S,G)를 인지한다.
  2. RP1은 TCP 639 세션 위로 SA message를 MSDP peer(RP2)로 전송한다.
  3. RP2는 SA를 수신해 peer-RPF 검증을 수행한다.
  4. 검증 통과 시 SA cache에 (S,G,R-originator)를 저장한다.
  5. RP2 측 receiver Join이 들어오면, RP2는 source 방향으로 PIM Join을 유도한다.
  6. 필요하면 SA를 다른 peer로 flood(또는 mesh-group 룰에 따라 제한)한다.

4-2. TCP 639 peering, connect-source, originator-id

MSDP session 자체는 TCP 기반이므로, 라우팅 도달성과 stable endpoint(loopback)가 중요하다.

  • connect-source loopback0: 세션 source를 unique Lo0로 고정한다.
  • originator-id loopback0: SA의 RP-originator 식별자도 unique로 유지한다.
  • Anycast 주소를 peer나 originator-id로 쓰면 RPF/중복 판정이 꼬일 위험이 크다.

4-3. SA message 의미

SA는 본질적으로 control 정보다. 핵심 필드는 { source S, group G, RP-originator R }이고, data encapsulation은 선택적 동작이다. 따라서 SA만으로 data plane이 즉시 열린다고 오해하면 안 된다. SA는 “소스가 있다”는 사실을 알려, 수신 측 RP가 Join을 시작할 수 있게 만든다.

4-4. SA cache와 peer-RPF

가장 많이 헷갈리는 지점이다. MSDP의 RPF 기준은 source S가 아니라 SA 안의 originating RP 주소 R다.

  1. 로컬 라우팅 테이블로 RP-originator R까지의 최적 경로를 계산한다.
  2. 그 경로의 next-hop에 해당하는 MSDP peer를 peer-RPF neighbor로 정한다.
  3. SA가 peer-RPF neighbor에서 들어오면 accept, 아니면 discard한다.
  4. accept한 SA만 downstream peer에게 flood한다(정책/mesh-group 조건 반영).
왜 이 규칙이 필요한가?
SA는 source 존재를 전달하는 control advertisement이기 때문에, “누가 이 advertisement를 시작했는지(RP-originator)”를 기준으로 경로 정합성을 보지 않으면 SA 루프/중복 확산을 통제하기 어렵다.

4-5. 주요 MSDP timer

Timer 일반 운영 값/의미 설명
SA Advertisement Period 동일 (S,G) 재광고 간격 제한 (예: 60초 이내 재전송 억제) 과도한 SA 재전송 방지
SA-State Timer SA cache 유지 시간 만료 시 재학습 필요
Hold Timer 일반 권장 75초 peer keepalive 미수신 시 세션 down 판정
KeepAlive 보통 60초 세션 생존 확인

“SA timeout 90초”에 대한 정직한 해석
현장에서 90초 내외 값이 관찰되는 Cisco 구현이 있지만, RFC 3618이 단일 고정값을 절대값으로 강제하는 것은 아니다. RFC 관점에서는 SG-State-Period ≥ (SA advertisement period + hold-down period) 같은 관계 조건이 핵심이다. 실제 장비 값은 반드시 현재 NX-OS release에서 show로 확인해야 한다.

4-6. Mesh-group

MSDP mesh-group은 SA flood 중복을 줄이기 위한 룰이다. 같은 mesh-group member에게서 받은 SA는 accept하되, 같은 mesh-group의 다른 member로 재전달하지 않는다.

이 룰이 제대로 동작하려면 mesh-group 내부가 full mesh여야 한다. 부분 연결이면 SA 전파 공백이 생길 수 있다.

5. vPC 환경에서 멀티캐스트가 실제로 동작하는 방식#

이 섹션은 운영 장애를 줄이는 핵심이다. vPC pair를 단순히 “L2 이중화”로만 보면 멀티캐스트 문제를 해석하기 어렵다.

5-1. vPC peer-link의 역할

  • vPC VLAN 트래픽 전달 기반
  • BUM flooding 보조
  • IGMP snooping learned group 공유
  • multicast forwarding state 동기화에 필요한 컨트롤 정보 전달

결과적으로 vPC pair는 multicast 관점에서, 논리적으로 하나의 forwarding system처럼 상태를 양쪽에 유지하려고 동작한다.

5-2. CFS 기반 IGMP snooping 동기화 (공개 범위)

공개 문서에서 확인 가능한 범위는 다음과 같다. 그룹 membership 공유, snooping state 동기화, 그리고 forwarder 결정에 필요한 상태 연동이다.

지적 정직성 메모
CFS 내부 메시지 포맷, 필드 구조, 내부 state machine 세부는 공개 문서로 완전히 확인되지 않는다. 본 문서는 공개 가능한 동작 결과와 show 명령 관찰 범위만 다룬다.

5-3. vPC forwarder election

일반적으로 source까지의 unicast metric을 비교해 forwarding peer를 고른다. metric 동률이면 vPC primary가 tie-break를 가진다.

  • forwarder peer: 해당 (S,G)에 대해 vPC OIF를 실제 보유하고 복제/전달을 담당
  • non-forwarder peer: state는 존재할 수 있으나 OIF가 0개일 수 있음

5-4. 핵심 개념: state 동기화와 forwarding 소유권은 다르다

중요
state가 양쪽에 존재하는 것과, 양쪽이 동시에 forward하는 것은 동일한 의미가 아니다. State synchronization ≠ forwarding ownership.

5-5. Receiver가 vPC에 연결된 경우 처리 순서

  1. Receiver host가 IGMP Report를 보낸다.
  2. Local peer가 IGMP snooping entry를 학습한다.
  3. peer-link/CFS를 통해 반대 peer와 그룹 상태를 동기화한다.
  4. 양쪽 모두 multicast 관련 state를 가진다.
  5. forwarder election 결과 한 peer가 forwarding ownership을 가진다.
  6. 선택되지 않은 peer는 중복 전송을 하지 않아 duplicate delivery를 방지한다.

5-6. Source가 vPC port-channel에 연결된 경우

이 케이스는 control-plane과 data-plane ownership이 어긋나기 쉬운 지점이다. 소스가 vPC port-channel 뒤에 있으면, 두 peer가 source를 local로 인식할 가능성이 있다.

  • duplicate Register 가능성
  • MSDP 사용 시 duplicate SA 가능성
  • forwarding owner와 registration owner 불일치 위험
반드시 명시해야 할 사실
모든 NX-OS release에서 “vPC source는 반드시 한 peer만 Register한다”는 일반 규칙을 Cisco 공식 문서로 단정하기 어렵다. 실제 Register originator는 show ip pim internal event-history null-register, 패킷 캡처, 플랫폼별 event-history로 검증해야 한다.

5-7. peer-link와 multicast RPF 관계

항목peer-link에서의 해석
vPC peer state 동기화가능
IGMP snooping state 공유가능

현장에서 자주 오해하는 문구가 “peer-link is not used for multicast RPF”이다. 이 문구는 “peer-link를 통한 state 동기화 자체를 금지”한다는 뜻이 아니라, PIM control-plane adjacency와 RPF topology를 peer-link에 의존하지 말라는 뜻이다.

NX-OS 제약 정리
vPC VLAN SVI와 downstream device 간 PIM adjacency는 일반적으로 지원되지 않으며, vPC SVI에서는 vPC peer 간 adjacency만 지원되는 형태로 문서화된다. 상세 지원 범위는 플랫폼/릴리스별 guide를 반드시 확인해야 한다.

6. RP를 어디에 둘 것인가 — vPC pair 내부 vs 외부#

6-1. vPC pair 자체가 RP인 경우 겹치는 역할

vPC pair 내부 RP 설계는 기능적으로 가능하지만, 한 장비에 다음 역할이 겹친다.

  • vPC state 동기화
  • Anycast-RP state 동기화(PIM Register copy 또는 MSDP SA)
  • DR/Register 처리
  • forwarder election
  • shared-tree 처리와 source state 관리

역할이 겹칠수록 장애 시 해석이 어려워지고, 원인 분리가 늦어질 수 있다.

6-2. Cisco가 경고하는 위험 시나리오

위험 시나리오
source VRF 트래픽이 non-forwarder vPC peer(그리고 그 장비가 RP)로 유입되면, forwarding owner peer에 (S,G) entry가 즉시 생성되지 않아 drop이 발생할 수 있다. Cisco 문서에서 이 토폴로지 위험이 언급되며, Anycast-RP 구성을 명시적으로 권고하는 배경이 된다.

6-3. vPC pair 내부 RP 배치 시 최소 5가지 조건

  1. Anycast 주소/unique 주소 분리(Lo1=5.1.1.1, Lo0=1.1.1.1/1.1.1.2) 엄수
  2. PIM Anycast-RP set 또는 MSDP peer/originator-id를 양쪽 완전 대칭으로 구성
  3. ip pim pre-build-spt 적용 여부를 장애 복구 목표(RTO) 기준으로 사전 판단
  4. 소스/리시버가 vPC 뒤에 있을 때 forwarder election 결과를 운영 대시보드로 상시 가시화
  5. peer-link 및 keepalive 장애 조합 시 시나리오 테스트(랩/점검창) 수행

6-4. RP를 외부(spine 등)에 두는 권장 모델

장점:

  • RP 역할과 vPC forwarding 역할을 분리해 장애 도메인 축소
  • leaf pair의 로컬 이벤트가 RP 제어 평면에 직접 결합되는 정도 감소
  • 트러블슈팅 경로 명확화(leaf 문제 vs RP 문제 분리)
  • TRM/EVPN 확장 시 spine 기반 정책 일관성 확보 용이

7. ip pim pre-build-spt#

vPC에서 forwarder만 upstream (S,G) Join을 보내는 기본 동작일 때, forwarder 장애가 발생하면 non-forwarder가 즉시 수신 준비가 안 되어 수렴이 느려질 수 있다.

문제 상황

  • 정상 시 non-forwarder의 (S,G) OIF가 0인 구조
  • forwarder 장애 시 대체 peer가 upstream Join을 새로 시작
  • 이 간격이 서비스 packet-loss window를 만든다

동작 원리

ip pim pre-build-spt를 쓰면, OIF가 0개인 상태에서도 source 방향 Join을 미리 보내 standby 성격의 SPT state를 사전 구축한다.

장점 3가지

  1. forwarder 장애 시 Join 재구축 지연 감소
  2. 수렴 예측 가능성 향상(장애 테스트 편차 감소)
  3. vPC source/receiver 혼재 구간에서 failover 체감 품질 개선

단점 2가지

  1. upstream 관점에서 중복 join/path 유지로 control/data 오버헤드 증가 가능
  2. 대규모 환경에서 대역폭/포워딩 리소스 사용량 증가 가능
운영 결론
Cisco vPC best-practice 맥락에서는, 다수 환경에서 수렴 이득이 대역폭 비용보다 크다고 보고 pre-build-spt를 권장하는 방향을 제시한다. 단, 실제 적용은 트래픽 패턴과 하드웨어 여유도를 함께 평가해야 한다.

설정 예시

feature pim

ip pim pre-build-spt

! VRF 별 적용이 필요한 릴리스에서는 다음과 같이 확인/적용
show running-config pim
show ip pim vrf PROD ?

8-1. peer-link만 다운 (keepalive 정상)

8-2. vPC peer 장비 전체 장애

surviving peer가 forwarding을 이어받는다. 이때 pre-build-spt 유무가 실제 수렴 체감에 큰 차이를 만든다.

  • RP가 외부면: peer 장애와 RP 기능 장애를 분리 가능
  • RP가 vPC pair 내부면: peer 장애가 곧 RP 가용성 이슈로 번질 수 있음

8-3. keepalive만 다운

keepalive 경로만 손실되면 peer liveness 판단이 어긋날 수 있다. split-brain 방지 동작은 role, peer-gateway, auto-recovery, dual-active detection 등 복합 요소에 의존한다.

검증 한계 명시
keepalive-only failure의 protocol별 상세 sequence를 모든 플랫폼/릴리스에 공통으로 단정할 수준의 공개 문서를 확보하기 어렵다. 운영 환경에서는 해당 릴리스의 공식 가이드 + 랩 재현으로 검증해야 한다.

8-4. RP 노드 reload 비교 (PIM Anycast-RP vs MSDP)

PIM Anycast-RP 케이스 (6단계)

  1. RP1 reload 시작, Anycast route 일부 철회
  2. IGP 수렴으로 DR/LHR이 RP2 경로로 이동
  3. 새 Register가 RP2로 유입
  4. RP2가 (S,G) 유지/재생성
  5. RP1 복구 후 Anycast route 재광고
  6. traffic은 IGP metric 기반으로 재분산

MSDP 케이스 (6단계)

  1. RP1 reload로 MSDP TCP session down
  2. peer hold timer 경과 후 RP2가 peer down 인지
  3. SA 유효성/캐시 만료 정책에 따라 source 정보 일부 소실 가능
  4. 새 Register/SA 재광고로 cache 재학습
  5. RP1 복구 시 TCP 639 재수립 + SA 교환 재개
  6. 정상화 속도는 timer와 session detection에 영향

8-5. 수렴 속도 비교 결론

intra-domain NX-OS 환경에서는, PIM Anycast-RP가 MSDP의 TCP session/SA flood 계층 없이 IGP 수렴 중심으로 경로가 바뀌므로 일반적으로 더 단순하고 빠르게 운영되는 경향이 있다.

정량 해석 주의
실제 packet-loss window는 IGP convergence, PIM Join-Prune timer, Register refresh, MSDP TCP failure detection, SA cache lifetime, vPC forwarder election, pre-build-spt 적용 여부가 함께 결정한다. 이는 RFC 동작과 Cisco 설계 권고에 기반한 일반 판단이며, Cisco가 모든 토폴로지에 대해 단일 정량 수치를 보장한다는 의미는 아니다.

10. VXLAN EVPN TRM 과의 관계#

underlay RP

TRM 설계에서 underlay RP는 일반적으로 spine 배치 + PIM Anycast-RP가 선호된다. leaf(vPC pair)에서 RP 기능을 분리해 장애 도메인을 줄이기 쉽기 때문이다.

overlay 모델

  • RP Everywhere
  • External RP

overlay 정책과 underlay RP 정책이 다를 수 있으므로, 한쪽 관점만 보고 전체 경로를 단정하면 안 된다.

외부 IOS/IOS-XE/IOS-XR RP 연동

외부 도메인과 SA 교환이 필요한 경우 Anycast MSDP가 필요할 수 있다. 이때 peer-RPF와 정책 필터를 포함한 MSDP 설계를 별도로 검증해야 한다.

vPC border leaf 주의사항

  • platform/release별 지원 범위 확인 필수
  • advertise-pip, advertise virtual-rmac 같은 EVPN 옵션과의 조합 검토
  • vPC peer 뒤 L3 source/receiver 지원을 위해 physical VRF-lite link가 필요한 토폴로지가 존재
  • peer-link만으로 L3 multicast reachability를 가정하지 말 것
현실적인 운영 포인트
TRM은 underlay/overlay/vPC 제약이 동시에 얽힌다. 반드시 “현재 운영 릴리스의 해당 플랫폼 가이드”로 교차 확인해야 한다.

12. 자주 발생하는 설정 오류 10선#

1) Anycast 주소와 unique 주소를 동일하게 사용

증상: Register/SA loop-prevention 또는 RPF 판정 이상, 상태 불안정

! 잘못된 설정
interface loopback0
  ip address 5.1.1.1/32
interface loopback1
  ip address 5.1.1.1/32

원인: Anycast 식별자와 unique 식별자가 충돌

! 올바른 설정
interface loopback0
  ip address 1.1.1.1/32   ! N9K-2는 1.1.1.2
interface loopback1
  ip address 5.1.1.1/32

2) Anycast RP loopback에 ip pim sparse-mode 누락

증상: RP 주소는 보이지만 Register 처리 실패

! 잘못된 설정
interface loopback1
  ip address 5.1.1.1/32
  ip router ospf 10 area 0

원인: RP 인터페이스에서 PIM 미활성

! 올바른 설정
interface loopback1
  ip address 5.1.1.1/32
  ip router ospf 10 area 0
  ip pim sparse-mode

3) ip msdp originator-id를 Anycast 주소로 설정 가장 흔한 오류

증상: MSDP 세션은 Established인데 SA discard 증가, SA cache 비정상

! 잘못된 설정
ip msdp originator-id 5.1.1.1

원인: duplicate RP address detection / peer-RPF 판정 충돌

! 올바른 설정
ip msdp originator-id loopback0   ! 1.1.1.1 또는 1.1.1.2

4) MSDP peer 주소에 Anycast 주소 사용

증상: 세션 flap 또는 비정상 RPF 동작

! 잘못된 설정
ip msdp peer 5.1.1.1 connect-source loopback0

원인: peer endpoint는 고정 unique여야 함

! 올바른 설정
ip msdp peer 1.1.1.2 connect-source loopback0   ! N9K-1 기준

5) MSDP peer-RPF mismatch

증상: session Established, 그러나 SA accepted counter 증가 없음 / SA cache 비어 있음

! 확인 명령
show ip msdp summary
show ip msdp peer
show ip msdp sa-cache
show ip route 1.1.1.2
show ip msdp statistics

원인: originator까지 최적경로와 SA 유입 peer 불일치

! 올바른 방향: 경로/피어 정합성 맞춤
! (예) IGP cost 수정 또는 MSDP 피어 재구성
ip router ospf 10
  auto-cost reference-bandwidth 100000

6) Anycast-RP set 설정 불일치

증상: 단방향 Register 복제, 일부 RP만 state 보유

! 잘못된 설정 (N9K-1에만 1.1.1.2 추가, N9K-2는 누락)
ip pim anycast-rp 5.1.1.1 1.1.1.1

원인: RP set 비대칭

! 올바른 설정 (양쪽 동일)
ip pim anycast-rp 5.1.1.1 1.1.1.1
ip pim anycast-rp 5.1.1.1 1.1.1.2

7) 두 방식(PIM Anycast-RP + MSDP) 동시 활성화

증상: 중복 source discovery, 분석 경로 모호화

! 혼합 상태 예시
ip pim anycast-rp 5.1.1.1 1.1.1.2
ip msdp peer 1.1.1.2 connect-source loopback0

원인: 동일 목적의 두 메커니즘 중복

! 올바른 설정: 설계 의도에 따라 하나만 선택
no ip msdp peer 1.1.1.2
! 또는
no ip pim anycast-rp 5.1.1.1 1.1.1.2

8) vPC peer-link를 PIM adjacency path로 사용하려는 시도

증상: adjacency 미형성, RPF 오해

! 잘못된 가정: peer-link를 외부 라우터 인접 경로로 활용
interface port-channel1
  ip pim sparse-mode   ! 설계 의도 불일치

원인: peer-link 역할 오해

! 올바른 방향: 외부 라우터와는 별도 L3 링크에서 PIM adjacency
interface Ethernet1/49
  ip address 172.16.0.1/31
  ip pim sparse-mode

9) pre-build-spt 누락으로 장애 시 수렴 지연

증상: forwarder failover 시 수신 복구 지연

! 누락 상태
show running-config pim

원인: 대체 peer의 upstream (S,G) Join 사전 준비 부족

! 올바른 설정
ip pim pre-build-spt

10) RP가 non-forwarder peer인 토폴로지

증상: 특정 source/VRF에서 간헐 drop, state는 있어 보이는데 전달 실패

! 문제 관찰 명령
show ip mroute detail
show ip pim internal event-history null-register
show forwarding distribution multicast route

원인: registration owner와 forwarding owner 비정합

! 완화 방향
ip pim pre-build-spt
! 또는 RP를 spine external Anycast-RP로 분리

13. 설계 의사결정 가이드#

PIM Anycast-RP를 선택하는 조건

  • 모든 RP가 NX-OS 또는 RFC 4610 상호운용이 검증된 동일 도메인 장비
  • inter-domain SA 교환 요구가 없음
  • 운영 단순성/수렴 속도를 최우선으로 둠
  • 트러블슈팅 경로를 PIM 중심으로 단순화하고 싶음
! 권장 구조(예)
ip pim rp-address 5.1.1.1 group-list 239.0.0.0/8
ip pim anycast-rp 5.1.1.1 1.1.1.1
ip pim anycast-rp 5.1.1.1 1.1.1.2
ip pim pre-build-spt

MSDP Anycast-RP를 선택하는 조건

  • 외부 도메인 또는 타 벤더 RP와 SA 교환이 필요
  • MSDP 운영/보안 정책(TCP MD5, SA filter)을 이미 갖추고 있음
  • peer-RPF, mesh-group, timer 튜닝을 운영팀이 소화 가능

MSDP 필수 설계 체크리스트

  • peer address는 반드시 unique Lo0
  • originator-id는 Anycast가 아닌 unique Lo0
  • peer-RPF 경로 정합성(IGP next-hop과 peer 일치)
  • mesh-group은 내부 full mesh
  • SA filter/보안정책/타이머를 운영 표준으로 문서화

14. 교육용 자가 점검 문제#

Q1. Anycast RP 주소와 Loopback0을 같게 쓰면 MSDP에서 무슨 일이 일어나는가?

정답 보기

originator-id와 peer-RPF 기준이 충돌해 SA가 discard될 수 있다. 현상은 session Established인데 SA cache가 비거나 accepted counter가 늘지 않는 형태로 나타난다.

Q2. vPC non-forwarder의 (S,G) OIF가 0인 것은 장애인가?

정답 보기

항상 장애는 아니다. vPC forwarder election 결과로 non-forwarder는 state만 갖고 OIF가 0일 수 있다. 실제 장애 판정은 forwarder peer 전달 상태와 IGMP/vPC 상태를 함께 확인해야 한다.

Q3. SA는 왜 source 주소가 아니라 originating RP 주소로 RPF 판정하는가?

정답 보기

SA는 source data 자체가 아니라 “source 존재 광고”이기 때문이다. 광고의 신뢰 경로를 판단하려면 advertisement origin(RP-originator)을 기준으로 peer-RPF를 계산해야 루프/중복을 통제할 수 있다.

Q4. pre-build-spt의 trade-off는?

정답 보기

장점은 failover 수렴 단축, 단점은 평시 중복 경로 준비로 인한 upstream 오버헤드와 포워딩 리소스 사용 증가 가능성이다. 즉, 수렴 vs 자원 소비의 교환관계다.

Q5. MSDP session이 Established인데 SA cache가 비어 있다면 무엇을 먼저 확인하는가?

정답 보기

1) peer 주소가 unique loopback인지, 2) originator-id가 유니크인지, 3) peer-RPF mismatch counter가 증가하는지, 4) SA 정책 필터가 과도하지 않은지 순서로 점검한다.

Q6. PIM Anycast-RP에서 복제 Register가 유실되면 source state는 영구히 없어지는가?

정답 보기

아니다. DR의 suppression timer 만료 후 Register 재전송으로 state가 재학습될 수 있다. PIM Anycast-RP는 persistent DB 복제보다 Register 이벤트 재생성 모델에 가깝다.

Q7. mesh-group이 full mesh가 아니면 왜 문제인가?

정답 보기

mesh-group 규칙은 “같은 그룹 내 재전달 억제”이므로, 내부 연결이 완전하지 않으면 SA가 특정 노드에 도달하지 못하는 블라인드 스팟이 생긴다.

Q8. RP가 vPC non-forwarder peer일 때 가능한 drop 시나리오는?

정답 보기

source 트래픽/등록이 non-forwarder 쪽으로 들어와 registration owner가 그쪽으로 치우치면, forwarding owner 쪽 (S,G) 준비가 지연되어 일부 흐름이 drop될 수 있다. 완화책으로 pre-build-spt 또는 external RP 분리가 사용된다.

15. 요약 — 7가지 핵심 정리#

  1. Anycast RP는 RP 선택 문제를 IGP로 단순화하지만, source 동기화 방식(PIM Register vs MSDP SA) 선택이 핵심이다.
  2. Nexus vPC 기준 기본 권장은 intra-domain에서 PIM Anycast-RP이며, 설정/운영 복잡도가 낮다.
  3. MSDP는 inter-domain·멀티벤더 연동에 강하지만 peer-RPF, mesh-group, timer 관리 역량이 필요하다.
  4. Anycast 주소(Lo1)와 unique 주소(Lo0) 분리는 두 방식 모두에서 필수 설계 원칙이다.
  5. vPC에서는 state 동기화와 forwarding ownership이 분리될 수 있으며, non-forwarder OIF 0은 정상일 수 있다.
  6. ip pim pre-build-spt는 수렴 향상에 유효하지만 자원 사용 증가 trade-off를 동반한다.
  7. 정량 수렴 시간, keepalive-only 장애 시퀀스, 일부 내부 동작은 release/platform 의존이므로 운영 버전 문서와 실측 검증이 필수다.
