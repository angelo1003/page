01 개요와 해결하는 문제

1.1 전통적(Regular) L3Out의 한계

ACI에서 외부 라우터/방화벽과 L3 라우팅 연동을 하려면 L3Out을 구성하고, 그 안에 Logical Interface Profile을 통해 border leaf의 물리 포트 → 외부 장비로 향하는 logical interface path를 명시해야 한다.

문제는 외부 장비가 가상 라우터/가상 방화벽이고, 하이퍼바이저 클러스터 위에서 동작할 때 발생한다. VMware DRS, vMotion, HA 등에 의해 VM이 임의의 호스트(= 임의의 leaf)로 이동할 수 있기 때문이다.

  • VM이 옮겨갈 수 있는 모든 leaf에 대해 logical interface path를 사전에 전부 수동 설정해야 한다.
  • 예: 하이퍼바이저 클러스터가 12개 leaf에 걸쳐 있으면, 12개 leaf 각각에 대해 L3Out logical interface를 만들어야 한다.
  • L3Out SVI와 VLAN 프로그래밍이 자동화되지 않으므로 설정량이 폭증하고, 외부 장비와의 routing peering 세션 수도 leaf 수만큼 증가한다.
전통적 L3Out 문제

1.2 Floating L3Out이 제공하는 것

Cisco ACI 4.2(1)부터 도입된 Floating L3Out은 개별 leaf마다 L3Out logical interface를 명시하지 않고 L3Out을 구성할 수 있게 한다. 핵심 가치는 두 가지다.

① 설정 단순화
VM이 이동해도 leaf마다 logical interface를 다시 만들 필요가 없다. APIC가 SVI / VLAN / floating IP를 자동으로 해당 leaf에 프로그래밍한다.
② Peering Scale 절감
오직 지정된 소수의 leaf(anchor leaf node)만 외부 라우터와 routing adjacency를 맺는다. ACI leaf 측과 외부 장비 측 모두 peering 부담이 줄어든다.
📌
도입 타임라인

4.2(1)은 VMware vSphere Distributed Switch(VDS) 기반 VMM 도메인만 지원했고, 5.0(1)부터 Physical Domain까지 확장되어 VMM 통합이 없는 가상 라우터나 물리 라우터 연결에도 사용할 수 있게 되었다.

02 핵심 개념과 용어

Virtual Router
ACI fabric에서 static route의 next-hop이 되거나 routing adjacency를 맺는 가상 라우터 / 가상 방화벽 등. 이동 대상이 되는 외부 장비.
Anchor Leaf Node ANCHOR
외부 라우터와 실제로 L3 adjacency(BGP/OSPF) 또는 static next-hop 종단을 맺는 leaf. Primary IP / Floating IP 사용(필요 시 secondary). 6.0(1) 기준 L3Out당 검증 스케일 = 6.
Non-Anchor Leaf Node NON-ANCHOR
외부 라우터와 adjacency를 맺지 않는 leaf. anchor로 향하는 트래픽의 "pass-through" 역할. Floating IP(및 floating secondary IP)만 사용. 6.0(1) 기준 L3Out당 검증 스케일 = 32.
Floating SVI
anchor / non-anchor에 공통으로 프로그래밍되는 L3 인터페이스. 동일 MAC을 모든 leaf에 심어, 외부 라우터가 어느 leaf 밑에 있어도 그 leaf가 직접 fabric으로 라우팅하게 한다.
External Bridge Domain
(L3Out's SVI subnet)
L3Out 구성 시 anchor node에 생성되는 BD. 동일 VLAN encap을 쓰면 같은 VNID로 매핑되어 anchor ↔ non-anchor 간 L2가 확장된다.

03 4가지 IP 주소의 역할

Floating L3Out의 SVI에는 최대 4종류의 IP가 관여한다. 이 구분이 설계의 핵심이다.

REQUIRED
Primary IP
각 anchor node · unique

해당 anchor SVI의 실제 IP. 외부 라우터와의 L3Out peering adjacency 종단.

OPTIONAL
Secondary IP
anchor node

① anchor들이 공유하는 virtual IP(static routing 시 외부 장비의 next-hop gateway) ② secondary subnet용 unique/공유 IP.

REQUIRED
Floating (Primary) IP
anchor + non-anchor 공통

모든 leaf에 동일 MAC으로 심어지는 L3 인터페이스. ARP resolution 및 외부→fabric 직접 포워딩에 사용.

OPTIONAL
Floating Secondary IP
anchor + non-anchor 공통

동일 External BD(SVI)에서 복수 subnet을 쓸 때만. 외부 통신용으로는 사용하지 않음.

⚠
설계 규칙

Primary IP와 Floating Primary IP는 반드시 동일 subnet에 속해야 한다.

3.1 IP 주소 배치 예시 (Cisco 문서 기준)

ip addressing
External BD VLAN encap = vlan-X,  Subnet 172.16.1.0/24

Leaf1 (anchor)   Primary        : 172.16.1.251/24
Leaf2 (anchor)   Primary        : 172.16.1.252/24
Leaf1/Leaf2      Secondary(공유) : 172.16.1.254/24   ← 외부 장비 static route next-hop
ALL leaf         Floating        : 172.16.1.250/24   ← ARP resolution, 동일 MAC

[추가 subnet이 같은 SVI VLAN에 필요할 때]
Secondary         : 172.16.2.254
Floating secondary: 172.16.2.250
  • 외부 장비는 fabric 내부 subnet(예: 192.168.1.0/24)으로 가는 static route의 next-hop을 172.16.1.254(secondary 공유 IP)로 설정.
  • non-anchor leaf도 floating IP(172.16.1.254 next-hop과 동일 MAC)를 인스턴스화하므로, 외부 라우터가 non-anchor 밑으로 이동해도 그 leaf가 직접 트래픽을 라우팅한다.

06 요구사항 (HW / SW / 버전 히스토리)

6.1 하드웨어 요구사항

!
Gen2 Leaf 필수

Generation 2 leaf switch 필수. Gen1 스위치는 anchor / non-anchor로 사용 불가. 단, Gen1 스위치를 non-border leaf(compute leaf)로는 사용할 수 있다.

6.2 소프트웨어 / 구성 요구사항

  • VLAN Pool: floating L3Out용으로 static VLAN range를 가진 VLAN pool이 필요.
    • VMM Domain 사용 시, L3Out domain의 VLAN pool과 VMM domain의 VLAN pool 범위가 동일해야 한다 (예: 양쪽 모두 200-209).
  • MTU: 1500 ~ 9216. inherit 지정 시 Fabric L2 MTU policy 값을 상속. 기본값 9000.

07 동작 방식: Control Plane / Data Plane

7.1 Control Plane

  • Anchor leaf node만 외부 라우터와 BGP/OSPF adjacency를 맺거나 static route의 next-hop 종단이 된다.
  • anchor가 외부 경로를 학습하면, 이를 MP-BGP VPNv4 fabric control plane을 통해 다른 leaf로 redistribution한다.
  • External BD(SVI subnet)는 동일 VLAN encap → 동일 VNID로 매핑되어 anchor와 non-anchor에 걸쳐 단일 L2 / broadcast 도메인을 형성한다. 그래서 외부 라우터가 non-anchor 밑에 있어도 anchor의 SVI와 L2로 연결되어 adjacency가 유지된다.

7.2 Data Plane — 기본(최적화 미적용) 흐름

외부 라우터가 non-anchor(Leaf3) 밑으로 이동한 경우(기본 동작):

traffic flow
[Inbound]  External → Leaf3(non-anchor) → Spine → Web EP(Host4)   ← 직접 (floating IP 동일 MAC)

[Outbound 기본 / Suboptimal]
  Web EP(Host4) → Spine → Anchor(Leaf1/2) → (다시 fabric) → Leaf3 → External
                              ▲ anchor가 외부 경로의 next-hop이므로 일단 anchor로 감
  • Inbound (External→Web): non-anchor가 floating IP(동일 MAC)를 갖고 있으므로 직접 fabric으로 라우팅한다.
  • Outbound (Web→External): compute leaf는 외부 prefix의 next-hop을 anchor를 통해 학습했으므로, 일단 anchor로 보냈다가 다시 non-anchor로 내려가는 비대칭 / Suboptimal 경로가 발생한다.
→

이 Suboptimal outbound 경로를 없애는 것이 8장의 주제다.

8.3 Multi-Protocol Recursive Route Resolution 5.2(1)+

BGP로 학습한 외부 prefix의 next-hop을 외부 라우터의 loopback IP로 두고, 그 loopback을 OSPF(또는 static)로 다시 학습시켜 다단계(recursive) 해석을 구성하는 방식. ECMP 확장에 핵심. (Next-hop propagation with Multipath를 추가로 활성화)

recursive resolution
BGP        :  10.0.0.0/8  via 1.1.1.1 (loopback)            ← 단일 primary next-hop
OSPF/static:  1.1.1.1     via 172.16.1.1, 172.16.1.2, 172.16.1.3  ← 다중 경로 (각 외부 라우터 직결 IP)
Direct adj :  172.16.1.x  via <Leaf TEP>                    ← 해당 leaf의 TEP

⇒ compute leaf가 동일 외부 prefix에 대해 여러 forwarder로 ECMP 가능
⚠
BGP ECMP 제약 (중요)

6.0(1) 기준, floating L3Out에서 BGP로 학습한 prefix는 compute leaf에 단 하나의 next-hop만 설치된다(IPv4/IPv6 공통). 즉 BGP만으로는 동일 prefix ECMP가 불가능하며, 위의 공통 loopback + recursive 해석 우회가 필요하다. (anchor 자신은 모든 경로 설치 가능)

i
프로토콜 분리 요건

BGP로 외부 route를, OSPF로 next-hop loopback을 광고하려면 L3Out을 2개(예: l3out-bgp, l3out-ospf)로 나눠야 한다. 단, 동일 floating SVI/VLAN encap을 "VRF" Encap Scope로 공유할 수 있다. 외부 route=BGP, next-hop loopback=static 조합이라면 단일 L3Out으로 가능.

8.4 Dedicated Control / Forwarding Node 분리 모델

  • Control node(BGP로 외부 prefix 광고)와 Forwarding node(OSPF/static + 실제 데이터 포워딩)를 분리.
  • forwarding node를 늘려 포워딩 용량만 확장하면서, control plane peering(BGP) 수는 늘리지 않을 수 있다.
  • control node는 floating L3Out 또는 일반 L3Out에 연결 가능(이동하지 않는 물리 장비면 일반 L3Out 사용 가능).

8.5 eBGP Multipath & Addpath 6.1(2)+

  • 이전: BGP peer는 control node 역할만, forwarding은 별도 노드 필요. anchor의 best-path 계산에 의존했고, directly-connected forwarder(metric 0)가 remote forwarder(metric 100)보다 우선되어, 둘이 공존하면 anchor가 directly-connected에 대해서만 multipath를 광고했다.
  • 6.1(2) 이상: eBGP peering을 forwarding node까지 직접 확장. anchor가 local metric과 무관하게 모든 unique next-hop을 fabric에 publish(addpath). directly / remote forwarder 모두 포함.
  • Ignore IGP Metric (VRF BGP Best Path Policy): directly-connected와 fabric 경유 next-hop의 local metric을 동일화하여 모든 next-hop을 ECMP 후보로 고려(필요 시 fabric으로 hairpin 감수). floating L3Out이 배포된 anchor/non-anchor 노드에만 설정 가능.

10 Multiple Encapsulation 지원

10.1 배경 5.2(3)+

기본적으로 동일 encap VLAN을 여러 leaf에 쓰면 동일 VNID로 매핑되어 하나의 External BD가 된다. 다른 VLAN을 쓰면 별도 External BD가 되었다(5.2(3) 이전엔 leaf마다 다른 VLAN으로 단일 BD 구성 불가).

5.2(3)부터 leaf마다 다른 VLAN encap을 쓰면서도 단일 External BD를 구성할 수 있다. (동일 VLAN을 다른 leaf에서 이미 쓰고 있어 재사용 불가한 경우 유용)

  • Floating SVI → physical domain의 Path Attribute(l3extRsDynPathAtt)로 leaf 세트별 VLAN 매핑.
  • Regular SVI → External Bridge Group Profile(l3extBdProfile)로 서로 다른 VLAN의 SVI들을 하나의 BD로 그룹화.
  • 6.0(1) 기준 Physical Domain L3Out만 지원 (VMM 미지원).

10.2 구성 패턴 예시 (Floating SVI)

multi-encap mapping
anchor  : node101, node102 → physDom1 / vlan100  (vPC pair → 동일 VLAN)
floating: node103, node104 → physDom2 / vlan101
floating: node105, node106 → physDom3 / vlan102
  • VLAN은 physical domain 단위로 프로비저닝되므로, encap이 다르면 domain/AEP를 분리해야 한다.
  • anchor의 Path Attribute는 Access Encap을 비워둠(anchor는 floating SVI의 encap=vlan100 사용). 다른 leaf용 domain은 해당 VLAN을 Access Encap에 지정.

10.3 Multiple Encapsulation 제약

  • Physical domain L3Out 전용(VMM 미지원).
  • 외부 장비/하이퍼바이저가 L2 loop를 차단한다는 전제. STP 의존 외부 스위치와 함께 쓰면 loop 위험.
  • External Bridge Group Profile 적용/변경 시 VLAN 재프로그래밍 → 트래픽 disruption 발생.
  • 각 access encap마다 별도 physical domain + AEP 생성, 그 노드들은 상호 비중첩(non-overlapping).
  • 동일 external bridge group 내에서 다른 VLAN encap을 가진 SVI는 같은 leaf에 프로그래밍 불가.
  • anchor 및 그 vPC pair는 단일 physical domain/AEP에 속해야 함.
  • SVI Encap Scope = Local 필수. VRF Encap scope 미지원.
  • 동일 floating SVI/bridge profile group에 동일 physical domain을 다른 VLAN으로 중복 구성 금지.

11 제약사항 및 고려사항 (Restrictions)

Cisco "Summary of Floating L3Out Deployment Considerations and Restrictions" 기준 정리.

11.1 도메인 / 기능 전제

  • Physical domain: 5.0(1) 이상 필요.
  • Next-hop propagation(Suboptimal 회피): Physical domain 전용, intra-VRF 전용. inter-VRF(consumer/provider 다른 VRF) 미지원.
  • Multicast routing (PIM, PIM6): floating SVI에서 미지원.

11.2 VMM Domain 관련

  • vRouter는 VMM domain이 생성한 port-group에 연결되어야 함.
  • 해당 port-group에 연결된 vRouter가 하나도 없으면 그 leaf에 floating SVI가 프로그래밍되지 않음.
  • DHCP client가 floating SVI로 연결될 경우, DHCP server는 floating SVI physical domain에 속한 동일 leaf(anchor/non-anchor)에 연결 금지.
  • Secondary floating IP는 5.0(1)부터 지원. 이전 릴리스로 downgrade 전 secondary 설정 제거 필요.

11.3 토폴로지 / 스위치 제약

!
설계 초기 확정 필요

Multi-Pod: pod에 걸친 배포는 지원되나, anchor와 non-anchor가 서로 다른 pod에 있으면 Suboptimal 회피(next-hop propagation/multipath) 미지원. (동일 pod면 internal EP는 어느 pod든 무방)
Remote Leaf: 미지원(remote leaf direct 활성화해도). remote leaf는 anchor/non-anchor로 배포 불가.

  • Generation 1 leaf: anchor/non-anchor 불가(compute leaf로만 사용 가능).
  • Per-port VLAN: floating L3Out 포트에서 미지원.
  • Non-anchor 노드는 logical node profile 아래에 구성 금지.

11.4 vPC / IP / Static Route

  • vPC interface로 외부 라우터를 연결하고 한쪽이 anchor면, vPC pair의 다른 쪽도 반드시 anchor여야 함. 동일 VLAN encap에서 anchor/non-anchor 혼합 불가.
  • Static route: 외부 라우터는 anchor의 primary 또는 secondary IP를 next-hop으로 사용해야 함.
  • Primary IP와 floating primary IP는 동일 subnet.
  • floating SVI와 non-floating SVI가 동일 VLAN encap으로 같은 leaf에 공존하려면 동일 primary IP를 사용해야 함.

11.5 IPv4 / IPv6 규칙

  • 동일 L3Out · 동일 leaf에서 IPv4/IPv6는 서로 다른 logical interface profile 필요.
  • Physical domain: 동일 VLAN encap이면 IPv4/IPv6 모두 동일 anchor 사용 필수(서로 다른 leaf 세트 불가).
  • VMM domain: 5.2(4) 이전엔 IPv4/IPv6 다른 VLAN encap 필요(port-group 분리). 5.2(4) 이상은 동일 encap 가능(단일 port-group). downgrade 시 동일 encap·다른 AF 동적 attachment 삭제됨.
  • recursive next-hop propagation 시 IPv6 link-local 미지원 → global address 사용.

11.6 Routing / Redistribution 동작

  • Attached host route(외부 라우터 IP)의 fabric 외부 광고: 5.2(1) 이전은 export rule 명시 시 광고 가능, 5.2(1) 이상은 기본적으로 외부 광고가 암묵적으로 deny됨.
  • BGP 학습 prefix는 compute leaf에 단일 next-hop만 설치(6.0(1), IPv4/IPv6). ECMP는 공통 loopback + recursive로 우회.
  • OSPF NSSA: forwarding node용 OSPF-only L3Out은 OSPF Area Type = NSSA 사용(next-hop을 global address로 학습하기 위해 type-7 LSA 필요).
  • static route에 다중 next-hop 사용 시 하나가 down되면 경로가 비최적일 수 있음 → CSCvy10946 참조.
  • CLI로 recursive next-hop propagation 구성 시: BGP peer에 next-hop unchanged route-map 미지원, route-profile template은 match rule 미지원.

11.7 알려진 결함(Bug) 및 주의

🐞
CSCwd28918

next-hop propagation 활성화 시, 여러 외부 라우터(control node redundancy)가 동일 외부 prefix를 동일 ECMP path로 광고하는 구성 비권장.

✅ 권장 서로 다른 next-hop IP — router1: 10.1.0.0/16 via 172.16.1.1, router2: ... via 172.16.1.2
❌ 비권장 동일 next-hop IP (둘 다 ... via 1.1.1.1) → ECMP 아님.

  • ECMP 트래픽 불균형: next-hop propagation으로 ECMP peer가 anchor/non-anchor에 걸쳐 연결될 때 분포가 불균등할 수 있음(anchor 뒤 장비가 트래픽을 적게 수신, Leaf 간 hairpin 발생 가능).
  • L3 next-hop 고사용 + IPv6 EP 다수가 동일 border leaf에 있으면 트래픽 drop 가능.
  • 수동 ARP clear 주의: non-anchor에서 외부 IP의 ARP를 수동으로 지우면 그 leaf가 외부 IP 광고를 멈춰 경로가 비최적이 됨. 모든 anchor/non-anchor에서 함께 clear해야 재최적화됨(IPv6 인접성도 동일).
  • UCS B-Series(FI 뒤 ESXi): Fabric Failover는 비활성화 권장. 활성화 시 LLDP/CDP가 active/standby vEth 양쪽에 보여 flapping/deploy 이슈 유발 → DVS 자체 redundancy 사용.

11.8 BFD / 수렴

⏱

VM 이동 시 1~2초 트래픽 손실 예상. BFD TX/RX ≥ 700ms 권장.

11.9 Nexus Dashboard Orchestrator(NDO) 연동

  • NDO 4.1(1) 이전: floating SVI 구성은 APIC 레벨(NDO에서 직접 구성 불가). 단, NDO가 floating SVI 포함 L3Out을 참조는 가능.
  • NDO 4.1(1) 이상: floating L3Out 포함 전체 L3Out 구성을 NDO에서 수행 가능. 단, next-hop propagation 등 floating L3Out 기능 자체는 각 fabric 내에서 동작.

12.2 핵심 설계 권고

  1. Anchor는 vPC pair 단위로
    외부 라우터가 vPC로 붙으면 vPC peer 둘 다 anchor. 안정적 adjacency와 redundancy 확보.
  2. Anchor 수는 redundancy + scale 균형
    L3Out당 anchor 6 / non-anchor 32(6.0.1 검증치)를 넘지 않도록, release별 Verified Scalability Guide 확인.
  3. BFD 700ms 이상
    false positive 방지하되 1~2초 이동 손실은 설계 SLA에 반영.
  4. ECMP가 필요하면 BGP 단독을 피하라
    공통 loopback + OSPF/static recursive(5.2.1+) 또는 eBGP multipath/addpath(6.1.2+) 채택. BGP 단독은 compute leaf에서 single next-hop.
  5. Control / Forwarding node 분리
    포워딩 확장과 control plane peering 수를 디커플링.
  6. BGP+OSPF 동시 필요 시 L3Out 2개
    l3out-bgp / l3out-ospf + 동일 floating SVI는 Encap Scope=VRF로 공유.
  7. Multi-Encap 사용 시 Encap Scope=Local
    domain/AEP를 encap별로 분리하고 노드 비중첩 유지.
  8. CSCwd28918 회피
    redundant control node는 서로 다른 next-hop IP로 광고.
  9. Multi-Pod에서 anchor/non-anchor를 같은 pod로
    Suboptimal 회피 기능 유지.
  10. Remote Leaf에는 floating L3Out 배치 불가
    설계 초기에 위치 확정.

12.3 사전 점검 체크리스트 (클릭하여 체크)

  • ✓모든 anchor/non-anchor가 Gen2 leaf인가?
  • ✓floating L3Out용 static range VLAN pool 준비(VMM이면 L3Out domain과 동일 범위)?
  • ✓Primary IP ↔ Floating Primary IP 동일 subnet?
  • ✓vPC anchor의 peer leaf도 anchor로 등록?
  • ✓static routing이면 외부 장비 next-hop = anchor primary/secondary IP?
  • ✓Suboptimal 회피/Multi-Encap 필요 → Physical domain으로 구성?
  • ✓inter-VRF 트래픽에 next-hop propagation을 기대하고 있지 않은가? (미지원)
  • ✓BFD 타이머 ≥ 700ms?
  • ✓Multi-Pod 배치 시 anchor/non-anchor 동일 pod?
  • ✓NDO 사용 시 버전(4.1(1)±)에 따른 구성 위치 확인?
  • ✓해당 릴리스 Verified Scalability Guide로 anchor/non-anchor/ECMP 스케일 재확인?
