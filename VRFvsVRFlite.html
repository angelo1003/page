01

핵심 요약 — TL;DR

VRF(Virtual Routing and Forwarding) 는 하나의 물리 라우터/스위치 안에 여러 개의 독립된 라우팅 테이블(RIB/FIB) 을 만들어 L3 트래픽을 논리적으로 분리하는 기술이다. 서로 다른 VRF는 IP 주소가 중복(overlap)되어도 충돌하지 않는다.

VRF Lite

// Multi-VRF CE
  • MPLS 없이 VRF만으로 분리
  • 구간마다 VRF별 분리 링크(802.1Q)
  • VRF별 라우팅 인스턴스를 hop-by-hop 구성
  • 모든 중간 장비가 모든 VRF를 인지
VS

MPLS L3VPN

// Full VRF
  • VRF + MP-BGP(VPNv4) + MPLS
  • PE(엣지)만 VRF를 인지
  • P(코어)는 레이블만 스위칭
  • 대규모 멀티테넌시에 최적
한 줄 정리

"VRF Lite는 코어 전체에 VRF를 흩뿌리는 방식, MPLS L3VPN은 코어를 레이블로 추상화하고 엣지에만 VRF를 두는 방식" 이다.

관점VRF LiteMPLS L3VPN
데이터 플레인네이티브 IP + 802.1QMPLS 레이블 스택
코어 장비의 VRF 인지모든 hop이 인지PE만 인지 (P는 모름)
확장성낮음 (수 개~수십 개 VRF)높음 (수천 VRF)
적합 영역캠퍼스, DC, 소규모 분리통신사 백본, 대규모 WAN
02

VRF란 무엇인가

2.1 정의

기본 라우터는 단 하나의 글로벌 라우팅 테이블을 가진다. VRF는 이 라우팅/포워딩 테이블을 여러 개의 독립 인스턴스로 가상화한다. 서버 가상화가 하나의 물리 서버를 여러 VM으로 나누듯, VRF는 하나의 L3 장비를 여러 개의 "가상 라우터"로 나눈다.

각 VRF 인스턴스는 다음을 독립적으로 소유한다.

🗂️
RIB

별도 라우팅 테이블 (Routing Information Base)

⚡
FIB / CEF

별도 하드웨어 포워딩 테이블

🔀
라우팅 인스턴스

OSPF process, BGP address-family 등 독립 인접성

🔌
인터페이스 소속

인터페이스/서브인터페이스의 VRF 바인딩

2.2 왜 VRF를 쓰는가 — 대표 Use Case

🏢

🔒

03

VRF의 구성 요소 : RD · RT · RIB · FIB

VRF Lite와 L3VPN의 차이를 이해하려면 이 네 가지 개념을 명확히 구분해야 한다. 특히 RD/RT는 MPLS L3VPN에서만 의미가 본격적으로 발현된다.

3.1 RIB / FIB

RIB — VRF별 라우팅 테이블
show ip route vrf RED
FIB(CEF) — VRF별 하드웨어 포워딩 테이블
show ip cef vrf RED
VRF의 본질

VRF Lite든 L3VPN이든 RIB·FIB는 항상 VRF별로 존재한다.

RD

// Route Distinguisher — "주소를 유일하게"
  • 8바이트(64bit) 를 IPv4(32bit) 앞에 붙여 VPNv4(96bit) 생성
  • 중복 IP를 전역적으로 유일하게 구분
  • 형식: ASN:nn 또는 IP:nn
  • ⚠️ 단지 유일성만 부여 — 정책 결정은 못 함

04

VRF Lite 심층 분석

VRF Lite = MPLS와 MP-BGP 백본 없이 VRF만으로 L3 분리를 장비 간에 확장하는 방식. 공식 명칭은 Multi-VRF CE 또는 VRF-Lite.

핵심 동작

"각 장비에 동일한 VRF들을 정의하고, 장비를 잇는 모든 구간을 VRF 개수만큼 논리적으로 쪼개서 각 VRF 전용 링크로 연결한다. 그리고 VRF별로 라우팅 프로토콜을 따로 돌린다."

VRF Lite — VRF가 코어 전체에 퍼진다

4.2 데이터 플레인

네이티브 IP 포워딩. MPLS 레이블 없음. 장비 간 구간에서 VRF를 구분하는 수단은 802.1Q 서브인터페이스(VRF마다 VLAN 태그 할당) 또는 VRF별 물리 인터페이스다. "와이어 위"에서는 VLAN 태그가 VRF를 구분하며, 패킷 자체에는 VRF 정보가 없고 인터페이스의 VRF 소속으로 결정된다.

4.3 컨트롤 플레인

VRF마다 별도의 라우팅 인스턴스를 운용한다 — OSPF는 VRF별 process, EIGRP/BGP는 address-family ipv4 vrf, Static은 ip route vrf. MP-BGP VPNv4 / MPLS 레이블 배포는 없다.

▲ 장점

  • 단순한 개념 — IGP만 알면 구성 가능
  • 광범위한 장비 지원 — L3 스위치·방화벽 등
  • 소규모 빠른 구축 — VLAN+VRF+IGP
  • 패킷이 IP라 디버깅 직관적

▼ 단점 ★아키텍트 필독

  • 확장성 폭발 — 구간마다 N개 서브IF
  • 경로상 모든 장비가 모든 VRF 유지
  • VRF 추가 시 전 구간 손봐야 함 (휴먼 에러)
  • No 트래픽 엔지니어링 (MPLS-TE/FRR 부재)

4.6 VRF Lite가 적합한 곳

캠퍼스/엔터프라이즈 망 분리(게스트·IoT·직원·OT, VRF 한 자릿수~십 단위) · 소규모 DC 멀티테넌시 · 방화벽 전후단/인터넷 에지 분리 · MPLS 역량/장비가 없는 환경 · L3VPN의 PE-CE 구간(여기선 VRF Lite가 표준).

05

MPLS L3VPN (Full VRF) 심층 분석

MPLS L3VPN = VRF + MP-BGP(VPNv4) + MPLS 레이블 스위칭. 통신사 L3VPN 서비스의 표준(RFC 4364, 구 2547bis).

핵심 아이디어

"엣지(PE)만 VRF를 알고, 코어(P)는 VRF를 전혀 모른 채 레이블만 스위칭한다. 고객 라우트는 MP-BGP가 VPNv4로 PE 간에 운반하고, 데이터는 2단 레이블 스택으로 전달한다."

설정 예시 — Cisco IOS / IOS-XE

문법

최신 통합 문법은 vrf definition + vrf forwarding 이다. (구 문법: ip vrf + ip vrf forwarding)

8.1 VRF 정의 (공통)

vrf-definition.cfgcisco
vrf definition CUST_RED
 rd 65000:1
 address-family ipv4
 exit-address-family
!
vrf definition CUST_BLUE
 rd 65000:2
 address-family ipv4
 exit-address-family

8.2 VRF Lite — 인터페이스 & 라우팅

vrf-lite.cfgcisco
! ─ 802.1Q 서브인터페이스로 VRF별 분리 ─
interface GigabitEthernet0/0.10
 encapsulation dot1Q 10
 vrf forwarding CUST_RED
 ip address 10.1.1.1 255.255.255.0
!
interface GigabitEthernet0/0.20
 encapsulation dot1Q 20
 vrf forwarding CUST_BLUE
 ip address 10.1.1.1 255.255.255.0     ! ← RED와 중복 IP, 문제 없음
!
! ─ VRF별 OSPF 프로세스 (서로 독립) ─
router ospf 10 vrf CUST_RED
 network 10.1.1.0 0.0.0.255 area 0
!
router ospf 20 vrf CUST_BLUE
 network 10.1.1.0 0.0.0.255 area 0

이 구성을 경로상의 모든 장비에 반복해야 한다는 점이 VRF Lite의 본질적 부담이다.

8.3 MPLS L3VPN — PE 라우터

pe-l3vpn.cfgcisco
! ─ VRF에 RT 추가 (import/export 정책) ─
vrf definition CUST_RED
 rd 65000:1
 route-target export 65000:100
 route-target import 65000:100
 address-family ipv4
 exit-address-family
!
! ─ 코어 인터페이스: MPLS 활성화 ─
interface GigabitEthernet0/2
 ip address 172.16.0.1 255.255.255.252
 mpls ip
!
! ─ 고객(CE) 대면 인터페이스: VRF 소속 ─
interface GigabitEthernet0/1
 vrf forwarding CUST_RED
 ip address 10.1.1.1 255.255.255.0
!
! ─ MP-BGP: VPNv4 + VRF별 PE-CE ─
router bgp 65000
 neighbor 2.2.2.2 remote-as 65000          ! 다른 PE (loopback)
 neighbor 2.2.2.2 update-source Loopback0
 !
 address-family vpnv4
  neighbor 2.2.2.2 activate
  neighbor 2.2.2.2 send-community extended  ! RT 전달 필수
 exit-address-family
 !
 address-family ipv4 vrf CUST_RED
  redistribute connected
  neighbor 10.1.1.2 remote-as 65001         ! CE와 eBGP
  neighbor 10.1.1.2 activate
 exit-address-family

8.4 검증 명령어

verify.shcisco
show vrf                         ! VRF 목록/인터페이스
show ip route vrf CUST_RED       ! VRF별 라우팅 테이블
show ip cef vrf CUST_RED         ! VRF별 포워딩
show bgp vpnv4 unicast all       ! VPNv4 라우트 (L3VPN)
show mpls forwarding-table       ! 레이블 테이블 (L3VPN)
ping vrf CUST_RED 10.1.1.2       ! VRF 컨텍스트 ping
traceroute vrf CUST_RED 10.1.1.2
09

VRF 간 라우트 누수 (Route Leaking)

완전 분리가 원칙이지만, 공유 서비스(인터넷·DNS·인증)를 위해 VRF 간 선택적 통신이 필요할 때가 있다.

9.1 MPLS L3VPN / MP-BGP — RT 기반 누수 (권장)

rt-leak.cfgcisco
vrf definition CUST_RED
 route-target export 65000:100
 route-target import 65000:100
 route-target import 65000:999    ! ← SHARED 서비스 라우트 가져오기
!
vrf definition SHARED_SVC

RT의 import/export 조합만으로 깔끔하게 누수를 제어한다. (확장 가능, 정책적)

9.2 VRF Lite / 순수 IP — 정적 라우트 누수

static-leak.cfgcisco
! VRF 간, 또는 VRF ↔ 글로벌 테이블 누수
ip route vrf CUST_RED 0.0.0.0 0.0.0.0 GigabitEthernet0/3 192.168.1.1 global
ip route vrf SHARED 10.1.1.0 255.255.255.0 GigabitEthernet0/1 10.1.1.1

global 키워드: VRF에서 글로벌 라우팅 테이블로 누수(인터넷 브레이크아웃에 흔함). 정적 누수는 단순하지만 확장성이 나쁘고 동적 변화에 약하다.

⚠️ 주의

라우트 누수는 VRF의 격리 목적을 의도적으로 깨는 행위다. 보안 세그멘테이션 용도라면 누수 지점에 방화벽/ACL을 반드시 둔다.

10.3 안티패턴 — 피해야 할 설계

❌ 대규모 VRF를 VRF Lite로 백본 전체에 확장 — hop마다 수십 개 서브인터페이스 → 설정·장애·운영 지옥.
❌ 소규모 분리에 MPLS L3VPN 풀스택 도입 — 과설계, 운영 부담만 증가.
❌ 라우트 누수 남발로 격리 무력화 — VRF 도입 의미 상실 + 보안 구멍.
❌ RD를 RT처럼 정책 도구로 오해 — RD는 유일성, RT가 정책.
11

확장성 · 운영 · 트러블슈팅

11.1 확장성 수치 감각

VRF Lite

"VRF 수 × 경로상 장비 수 × 인접성"이 곱셈으로 증가. 실무상 VRF 8~16개, hop 3개 이하를 넘으면 관리가 급격히 어려워진다.

MPLS L3VPN

PE의 VRF/RIB 용량과 RR(Route Reflector) 설계가 한계를 좌우. 수천 VRF도 정상 운용.

11.2 운영 관점 체크포인트

  • VRF 컨텍스트 인지 — ping/traceroute/ssh 시 반드시 vrf 키워드. 글로벌에서 쏘면 도달 불가.
  • MTU — MPLS 레이블(4B/레이블) MTU 감소, 코어 점보프레임 권장. VRF Lite는 802.1Q(4B) 고려.
  • 관리망 — Mgmt-vrf 분리 시 NTP/SNMP/AAA/Syslog 소스 인터페이스를 VRF로 명시.
  • 재분배 — VRF별 IGP↔BGP 재분배 루프/서브옵티멀 라우팅 주의.

11.4 흔한 실수

L3VPN에서 send-community extended 누락 → RT 전달 안 됨 → import 실패.
VRF Lite에서 encapsulation dot1Q 또는 양단 VLAN 불일치.
vrf forwarding 적용 시 기존 IP 제거됨 → 재설정 필요(운영 중 끊김).
글로벌 테이블 기준 관리 접속 시도 → VRF 도달성 실패.
12

현대적 대안 : EVPN/VXLAN · SR · SD-WAN

VRF의 "L3 세그멘테이션" 요구는 현대 아키텍처에서 다음으로 진화/대체되고 있다.

🧬
EVPN / VXLAN (DC)

VXLAN VNI로 L2/L3 오버레이, VRF는 L3VNI에 매핑. MP-BGP EVPN이 컨트롤 플레인. 대규모 멀티테넌트 DC의 사실상 표준.

➡️
SR-MPLS / SRv6

LDP를 SR로 대체해 코어 단순화·TE 강화. L3VPN 개념은 그대로, transport만 SR.

☁️
SD-WAN

VRF/세그먼트를 오버레이 터널 + 중앙 컨트롤러로 추상화. 지점 간 세그멘테이션을 정책으로 관리.

정리

VRF Lite ↔ MPLS L3VPN의 선택 논리는, DC에서는 "플랫 VRF Lite ↔ EVPN/VXLAN", WAN에서는 "MPLS L3VPN ↔ SR/SD-WAN" 으로 형태만 바뀌어 동일하게 반복된다.
