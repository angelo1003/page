증상 & 목표

⚠증상

외부에서 OSPF로 학습된 경로가 cost로 인해 Remote(타 사이트) L3Out을 우선하는 경우 발생.

◎목표 — Per-Site Locality

Site1 Leaf → Site1 L3Out, Site2 Leaf → Site2 L3Out 을 각각 우선. Remote L3Out은 백업으로만 사용.

★가장 중요한 포인트

이것은 "한 사이트를 전역 우선"하는 것이 아니다. 각 사이트가 자기 로컬 L3Out을 우선해야 한다. 따라서 전역으로 전파되는 Local Preference를 쓰면 안 된다 — 사이트 로컬에만 머무는 BGP Weight 가 정답이다.

근본 원인 & 동작 원리

1-0전제 — 두 L3Out이 서로 보이려면 Intersite L3Out이 필요

Intersite L3Out 미구성

두 사이트 L3Out은 완전 독립. Site1 Leaf는 Site2 L3Out 경로를 아예 보지 못함 → 자동으로 로컬만 사용(문제 없음).

Intersite L3Out 구성

한 사이트 외부 prefix가 EVPN으로 타 사이트에 백업 경로로 광고됨. 이때부터 "어느 L3Out을 쓸지" 선택이 발생.

ℹ역추론

Remote L3Out이 보이고 그게 우선되는 상황이면 → Intersite L3Out이 켜져 있다는 의미다.

1-1기본 동작 — 사이트 로컬 우선은 원래 자동

동일 외부 prefix를 양쪽 L3Out이 광고하면, fabric leaf에는 두 경로가 보인다.

① 로컬 BL 경유 선호

로컬 L3Out → OSPF → fabric에 로컬 originate, Weight 높음, 로컬 BL TEP next-hop, 짧은 IS-IS 메트릭.

② Remote BL 경유 백업

EVPN으로 import된 타 사이트 경로, Weight 0.

✓결론

각 사이트 Leaf는 로컬 originate·높은 Weight 경로를 우선 → Per-site locality는 원래 기본 동작이다.

1-2그런데 왜 Remote가 우선되나

기본 로컬 우선이 깨지는 조건:

OSPF cost → MED 전달

redistribution 시 로컬 경로 메트릭이 Remote보다 나빠짐 (가장 흔한 원인)

Host route / prefix 광고 차이

특정 prefix가 더 정밀하게 광고되어 선택 역전

Intersite L3Out · transit 구성

경로 선택 이상 유발

외부 BGP 속성

MED / AS-Path가 선택에 영향

1-3해결의 핵심 — Local Preference가 아니라 Weight

✗Local Preference (전역 전파)

iBGP이므로 EVPN을 타고 타 사이트로 전파. Site1에 Local-Pref를 높이면 Site2 Leaf까지 Site1 L3Out을 우선 → per-site locality 붕괴(전역 우선).

✓BGP Weight (사이트 로컬)

비전이(non-transitive) 속성 — 어떤 BGP peer에게도 광고되지 않고 해당 Leaf/사이트 로컬에만 머문다. 각 사이트가 독립적으로 자기 로컬 L3Out을 우선.

로컬 경로 (Weight 100, 선호) Inter-Site EVPN 백업 (Weight 0)

1-4✅ 검증 — "iBGP인데 Weight가 사이트 간 전달 안 되는 게 맞나?"

✓✓✓결론: 맞다 — Weight는 iBGP·eBGP 어떤 peer에게도 절대 전달되지 않는다 (3중 확인)
①BGP 프로토콜 (RFC 4271)

Weight는 BGP path attribute가 아니다. RFC 4271의 transitive/non-transitive attribute 목록에 존재하지 않음. BGP UPDATE 메시지에 인코딩되지 않는 순수 로컬 RIB 선택값 → 메시지에 안 실리므로 전달 자체가 불가.

②Cisco 공식문서 213285

"Understand the Importance of BGP Weight Path Attribute" (2025-04 recert) 원문 확인.

③ACI Multi-Site 동작

spine의 EVPN translation은 Weight를 재생성/전파하지 않음. community→weight 매핑·table-map 등 remote에서 weight를 복원하는 자동 메커니즘 없음 (Multi-Site Troubleshooting Guide).

Cisco Doc ID 213285 — 원문 인용
"Weight is a Cisco-specific parameter and it is only
 LOCALLY SIGNIFICANT in the Router where it is configured."

"The weight is assigned locally to the router. The value is
 NOT PROPAGATED or carried through any of the route updates."

# → BGP best-path 알고리즘에서 가장 먼저 비교되는 값 (highest wins)

대조 — 왜 Local Preference는 안 되는가

Local Preference Well-known attr (type 5) ✓ 전달됨 ✗ 안 됨 타 사이트 전파 → 전역 우선 ❌
★핵심 차이

동일 ASN이라 두 사이트가 iBGP인데, Local-Pref는 iBGP 내부에서 전달되는 속성이라 Site2까지 넘어간다. 반면 Weight는 BGP 메시지에 아예 실리지 않아 ASN이 같든 다르든 무관하게 사이트 로컬에만 머문다.

✓최종 정리

Site1 BL에 Weight 100 설정 → Site1 Leaf들만 영향. Site2 Leaf들은 같은 prefix를 iBGP EVPN으로 학습하되 Weight는 기본값 0 그대로. 양쪽에 각각 100을 주면 각 사이트가 독립적으로 자기 BL 우선. ✅

1-5그럼 Weight는 "어디에 설정되어" 동작하나

★관점 전환

Weight는 "보내는 값"이 아니라, 경로를 받아들이는 라우터(Leaf)가 자기 BGP 테이블(RIB-In)에 저장할 때 로컬로 붙이는 표식이다. 그래서 "어디로 광고되나"가 아니라 "어느 Leaf에서 설정되나" 가 전부다.

동작 위치 = 각 사이트의 Border Leaf (BL) — BL이 OSPF 외부경로를 fabric MP-BGP로 redistribution(Interleak)하는 그 순간, 해당 BL의 BGP 프로세스가 자기 RIB에 경로를 넣으면서 Weight를 부여한다. 이 값은 그 BL(및 같은 fabric 내 Leaf)에만 존재하고 best-path에서 가장 먼저 비교된다.

EVPN UPDATE — prefix/NH/AS-path만 전송 (Weight 미포함)
같은 prefix인데 사이트마다 Weight가 다른 이유
위치Weight왜
Site1 Leaf (BL 포함)100BL이 redistribution 시 로컬 설정 (로컬 originate)
Site2 Leaf0EVPN UPDATE에 Weight 없음 → iBGP 학습 기본값

→ 동일 값이 전파된 게 아니라, 각 Leaf가 자기 관점에서 독립적으로 Weight를 매긴 결과.

비유 — 운송장 vs 창고 스티커

Local Preference = 운송장 → iBGP 트럭에 실려 Site2 창고까지 따라감 ❌

Weight = 창고 내부 스티커 → Site1이 붙인 건 Site1에만, Site2는 자기 스티커(기본 0)를 따로 붙임 ✅

ℹ"사이트 로컬에 머문다"의 정확한 의미

전파를 차단한다는 뜻이 아니라, 애초에 전파 대상이 아니고 각 Leaf가 자체적으로 RIB-In에 생성한다는 의미. 그래서 ASN이 같아도(iBGP) 전혀 새지 않는다.

2

권장 해결책 (우선순위 순)

방안 A · 핵심

Route Map으로 Weight 상향 — Per-Site Locality

각 사이트에서 로컬 redistribution 경로에 높은 BGP Weight 부여(예: 100). Weight는 사이트 로컬에만 머물고 타 사이트로 전파되지 않으므로, Site1·Site2가 각자 자기 로컬 L3Out을 독립적으로 우선한다.

✗Set Preference(Local Preference) 사용 금지

iBGP EVPN으로 전파되어 전역 우선이 되며 per-site locality가 깨진다.

방안 B · 보조

OSPF Cost 튜닝

BL에서 로컬 L3Out OSPF interface cost를 낮춰 MED를 줄임. 방안 A와 병행 권장.

방안 C · 인그레스

Host Route Advertisement

BD 단위 활성화(ACI 4.0+)로 리턴 트래픽이 EP 위치 사이트로 들어오게 유도. 비대칭 라우팅 완화.

방안 D · 설계

Intersite L3Out 검토

Remote 백업이 불필요하면 해제 → 두 L3Out 완전 독립 → per-site locality 자동 보장(가장 단순).

3A

Match Rule / Set Rule 상세 구성

★역할 분담

Weight를 "어떤 경로에" 줄지는 Match Rule(매칭 대상 prefix)이, "무엇을 줄지"는 Set Rule(Set Weight)이 담당. Route Control Context 안에서 둘을 묶는다.

A-1Set Rule 생성 (Set Weight) — 공통

Tenant›Policies›Protocol›Set Rules for Route Maps
  1. Create Set Rules for Route Maps
  2. Name: SET-WEIGHT-100
  3. Set Weight 체크 → Weight = 100 (유효 범위 0–65535)
  4. Preference / Community / AS-Path 항목은 건드리지 않음
  5. Submit

A-2Match Rule 생성 (대상 prefix) — 두 가지 방식

①특정 prefix만 (권장 · 정밀)
Tenant›Policies›Protocol›Match Rules for Route Maps

Name: MATCH-EXT-PREFIXES → Match Prefix 추가:

필드값 예시설명
IP10.0.0.0/8로컬 우선시킬 prefix
Aggregate☑ (=le 32)하위 서브넷 포함
ge (Greater)비움 / 8최소 길이

②모든 경로 일괄 (Match 생략)

Match Rule은 필수가 아니다. Route Control Context를 Action=Permit + Set Rule만 지정하면 모든 경로 매칭.

모든 외부 prefix를 로컬 우선시키려면 Match Rule 없이 Context에 SET-WEIGHT-100만 연결. (또는 방식①의 0.0.0.0/0 le 32로 동일 효과)

3B

Site1 / Site2 각각 적용 (핵심)

★가장 중요 — 양쪽 다 Weight 100

Weight는 사이트 로컬이므로, 양쪽 사이트가 "각자 자기 로컬 L3Out 경로를 매칭해" 동일한 Weight(100)를 주면 각 사이트가 독립적으로 자기 BL을 우선. 사이트별로 다른 값을 줄 필요 없음 — 양쪽 다 100이 정답.

◎핵심 개념

각 사이트는 자기 L3Out에만 Weight를 박는다. Weight는 전파 안 되므로 Site1의 100이 Site2로 넘어가지 않음 → 충돌·전역 우선 없음.

방법 1각 사이트 APIC에서 개별 설정

[ Site1 APIC ]
  1. Tenant › Policies › Protocol
    • Set Rule SET-WEIGHT-100 (Weight 100)
    • Match Rule MATCH-EXT-PREFIXES
  2. L3Outs › L3Out-Site1 › Route map import/export
    • Context: Order 10 / Permit / Match+Set
    • default-import (Interleak) 연결
  3. Submit → Site1 BL 경로 Weight 100
[ Site2 APIC ]
  1. Tenant › Policies › Protocol — 동일하게
    • Set Rule SET-WEIGHT-100
    • Match Rule MATCH-EXT-PREFIXES
  2. L3Outs › L3Out-Site2 › Route map import/export
    • Context: Order 10 / Permit / Match+Set
    • default-import (Interleak) 연결
  3. Submit → Site2 BL 경로 Weight 100
✓결과

Site1 Leaf: Site1 BL(W100) vs Remote(W0) → Site1 우선 · Site2 Leaf: Site2 BL(W100) vs Remote(W0) → Site2 우선

방법 2NDO 중앙 배포 권장

  1. NDO › Route Map Template 생성: Match(MATCH-EXT-PREFIXES) + Set(SET-WEIGHT-100)
  2. 이 템플릿을 양쪽 사이트 L3Out의 import/interleak route control에 연결
  3. Template-to-Site 매핑: Site1 템플릿 → Site1 배포 / Site2 템플릿 → Site2 배포
  4. Deploy → 두 사이트에 동일 Weight 정책 일관 적용, 드리프트 방지

NDO에서는 사이트별 L3Out object에 같은 Route Map을 attach하되, 각 site에 배포되어 그 사이트의 로컬 BL 경로에만 적용된다.

3C

향후 트래픽 엔지니어링 — Context Order 동작

★질문: Order 1·2·3 중 1에 매칭되면 2·3은 적용 안 되나?

→ 그렇다. First-Match-Wins. 먼저 매칭된 Context의 Set만 적용하고 평가 종료 — IOS/NX-OS route-map과 동일.

C-1평가 규칙

  • Context는 Order 오름차순(1 → 2 → 3) 평가
  • 먼저 매칭된 Context의 Set만 적용하고 종료 → 이후 Order는 그 경로에 적용 안 됨
  • 한 경로 = 하나의 Context만 적용 (누적·덮어쓰기 아님)

C-2TE 설계 실무 포인트

①그룹이 안 겹치면 Order 무의미

각 prefix가 자기 그룹 Context에만 매칭 → Order 무관 독립 동작. 그룹별 다른 Weight(300/200/100) TE 정상 동작.

②겹치면 낮은 Order 승 & 종료

group1·group2 둘 다 매칭 가능 prefix → Order 낮은 쪽(1) 적용 후 종료, group2 무시.
→ 더 구체적/우선 그룹을 낮은 Order에 배치.

C-3⚠️ 가장 주의 — Implicit Deny (catch-all 필수)

⚠매칭 안 된 경로는 전부 DROP된다

ACI route-map도 IOS처럼 맨 끝에 implicit deny가 있다. 어느 Context에도 매칭 안 된 prefix는 deny 처리되어 redistribution/import에서 누락. 일부 그룹에만 Weight를 주면 나머지 경로가 통째로 사라질 위험.

✓해결 — catch-all Permit

맨 끝(가장 높은 Order)에 catch-all Permit Context(Match=0.0.0.0/0 le 32, Set 없음)를 둬서 나머지 경로를 Weight 변경 없이 통과시킨다.

C-5빈 Match에 Set이 있으면? (나머지에만 적용 — 앞 그룹은 안 건드림)

예시 — 마지막 Order 9의 Match를 비움
Order 1 : Match GRP1   Set MED 50                Permit
Order 2 : Match GRP2   Set MED 10, Weight 200    Permit
Order 3 : Match GRP3   Set MED 10, Weight 100    Permit
Order 9 : (Match 비움) Set MED 10, Weight 300  Permit
✓핵심 — First-Match-Wins

각 경로는 처음 매칭된 Context만 적용하고 거기서 STOP. GRP1 대역 → Order 1에서 MED 50 적용하고 멈춤. Order 9는 GRP1에 절대 적용 안 됨. GRP1의 Weight는 Order 1이 미설정이라 기본값 0(Order 9의 300이 오는 게 아님). 빈 Match(Order 9)는 GRP1/2/3 어디에도 안 걸린 "그 외" 대역에만 적용.

⚠주의 1 — Order 9는 "투명 통과"가 아님

빈 Match라도 Set이 있으면 "그 외" 경로 전부에 그 값을 적극 설정(앞 그룹이 아니라 나머지에). implicit deny만 막고 나머지 값도 안 바꾸려면 → Set을 비워야 한다 (Match 없음 + Set 없음 + Permit). 위 config는 "그 외" 경로가 Weight 300(최고) 을 받음.

⚠주의 2 — 적용 단계 vs best-path 단계는 별개

"GRP1이 밀린다"는 Order 9가 GRP1을 덮는다는 뜻이 아니다. 두 단계를 구분:
① route-map 적용(first-match): GRP1=MED50/W0 확정 (Order 9 무관)
② best-path 선택: 확정된 속성으로 경로 비교. 동일 목적지에 복수 경로가 있을 때만 Weight 비교 발생.

best-path 단계에서만 — Weight 비교

best-path decision order
Weight(高 우선) → Local-Pref(高) → Locally originated → AS-Path(短)
  → Origin → MED(低 우선) → eBGP>iBGP → IGP metric → ...
# 동일 목적지에 GRP1 경로 + 다른 경로가 동시에 있을 때만 W0인 GRP1이 밀림
# GRP1/2/3가 서로 다른 목적지면 best-path 경쟁 자체가 없음 → GRP1 그대로 동작
✓권장 — 속성 통일 (혼용 금지)

같은 라우터(사이트) 안 우선순위만 → Weight만 사용(MED 빼기). 외부 eBGP 피어로 광고해 인바운드 유도 → MED만 사용(Weight는 외부로 안 나감). MED는 외부 광고되지만 Weight는 로컬 전용 — 목적에 맞는 하나로 통일해 혼용을 피한다.

방안 B 상세 (OSPF Cost · 보조)

  • 로컬 L3Out의 OSPF interface cost를 낮춤 (Logical Interface Profile › OSPF Interface Policy / per-interface cost)
  • redistribution 시 MED가 작아져 동률 비교에서 로컬 우선에 유리
  • 방안 A(Weight)와 병행 시 가장 견고

검증 (Border Leaf CLI)

border-leaf# verify
# VRF 라우팅 테이블 — 어느 경로가 설치됐는지
show ip route vrf <vrf-name>

# EVPN 테이블 — weight / best-path 확인
show bgp l2vpn evpn vrf <vrf-name> <prefix>

# VRF 내 BGP IPv4 — weight / 선택 경로 확인
show bgp ipv4 unicast vrf <vrf-name> <prefix>
확인 포인트
  • 로컬 L3Out 경유 경로의 weight가 더 높은지(100), Remote 경로는 weight 0
  • 해당 로컬 경로가 best-path(>)로 선택되는지
  • 로컬 BL의 next-hop(로컬 TEP)이 선택되는지
  • Site1·Site2 양쪽 Leaf에서 각각 자기 로컬 경로가 선택되는지 (전역 우선이 아님)

적용 범위 (APIC vs NDO)

각 사이트 APIC 개별 설정

사이트별로 Route Map 생성 + L3Out 적용.

NDO 중앙 배포 권장

Route Map 템플릿을 L3Out external EPG / route control에 연결해 일관 배포. 다중 사이트 일관성 확보에 유리.

✓권장

Multi-Site는 NDO에서 템플릿으로 관리하여 양 사이트 정책 드리프트 방지.

7

적용 순서 (권장 워크플로우)

  1. (변경 전) 현재 best-path 캡처: show bgp ipv4 unicast vrf ... 로 baseline 저장 (Site1·Site2 양쪽)
  2. 방안 A 적용 (로컬 redistribution 경로에 Weight 100) — 양쪽 사이트 L3Out에 각각 적용
  3. 검증 명령으로 각 사이트가 자기 로컬 BL 경로를 선택하는지 확인
  4. 필요 시 방안 B(OSPF cost) 병행
  5. 인그레스 비대칭이 있으면 방안 C(Host Route Advertisement) 추가
  6. Remote 백업이 불필요하면 방안 D(Intersite L3Out 해제) 검토
